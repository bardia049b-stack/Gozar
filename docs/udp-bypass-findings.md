# آزمون دور زدن محدودیت UDP در رلهٔ MASQUE موزیلا

تاریخ آزمون: ۲۰۲۶‑۱۱‑۰۲ — سرور آزمون: `ehrd229.m1.fastly-masque.net` (NL) و `muc139.m1.fastly-masque.net` (DE)، پورت ۲۴۹۹

## ۱. چه چیزی روی شبکه اندازه‌گیری شد

| آزمون | نتیجه |
|---|---|
| TLS/TCP روی ۲۴۹۹ با ALPN `h2` | موفق (TLS 1.3، ALPN=h2) |
| TLS/TCP روی ۲۴۹۹ با ALPN `http/1.1` | موفق |
| TLS/TCP روی ۲۴۹۹ با ALPN `h3` | رد شد (no_application_protocol) — طبیعی، چون h3 روی UDP است |
| QUIC/UDP روی ۲۴۹۹ با ALPN `h3` | موفق؛ پاسخ‌های HTTP/3 واقعی از لبهٔ Fastly |
| `CONNECT` ساده در H3 | `400` + `X-Fastly-Proxy-Auth-Failed: parse_failure` / «parsing JWT failed» |
| extended CONNECT `connect-tcp` | همان پاسخ |
| extended CONNECT `connect-udp` (به `1.1.1.1:53`) | همان پاسخ |
| `connect-udp` به پورت بالا (۳۰۷۴) | همان پاسخ |
| extended CONNECT `connect-ip` | همان پاسخ |
| توکن بدیهی (`bogus.jwt.value`) | همان پاسخ |
| JWT ساختگی خوش‌ساخت (EdDSA, base64url) | همان پاسخ |
| **کنترل: `:protocol = foo-bar`** | **همان پاسخ** |

## ۲. نتیجهٔ کلیدی

آزمون کنترل تعیین‌کننده است: حتی پروتکل کاملاً بی‌معنی هم دقیقاً همان خطای احراز هویت را می‌دهد. یعنی **لبهٔ Fastly اول JWT را بررسی می‌کند و بعد به وجود یا نبود `connect-udp` نگاه می‌کند.** پس با درخواست بدون توکن نمی‌شود فهمید UDP پشتیبانی می‌شود یا نه — و برعکس، رد شدن `connect-udp` هم چیزی را اثبات نمی‌کند.

آنچه قطعی است:
- مسیر QUIC/HTTP/3 روی همان پورت ۲۴۹۹ باز است (نه فقط H2 روی TCP).
- احراز هویت برای همهٔ انواع CONNECT یکسان است (`Proxy-Authorization: Bearer`).
- سرورلیست عمومی موزیلا ۳۵ کشور دارد و همه روی پورت ۲۴۹۹ با میزبان‌های `*.m1.fastly-masque.net` هستند؛ هیچ فیلد `protocol`/`templateString` عمومی منتشر نشده است.

## ۳. آزمون سمت کلاینت (پروف آف کانپت)

یک کلاینت مستقل با quic-go نوشته شد:
- ایجاد تونل `connect-udp` روی یک سرور محلی → پاسخ `200` گرفته شد.
- دیتاگرام از سرور به کلاینت رسید و درست رمزگشایی شد.
- دیتاگرام از کلاینت به سرور در پروف فعلی نرسید (جزئیات API در quic-go؛ حل نشده).

یعنی «شکل کار» درست است ولی هنوز یک تونل UDP سرتاسریِ تأییدشده نداریم.

## ۴. جمع‌بندی

| پرسش | پاسخ |
|---|---|
| آیا رله QUIC/H3 قبول می‌کند؟ | بله، قطعی |
| آیا `connect-udp` از دید HTTP پذیرفته می‌شود؟ | نمی‌دانیم؛ احراز هویت جلوتر از بررسی پروتکل است |
| آیا محدودیت پورت (۸۰/۴۴۳/۸۰۸۰/۸۴۴۳) برای UDP هم هست؟ | نمی‌دانیم؛ بدون توکن معتبر قابل سنجش نیست |
| آیا الان می‌شود در برنامه فعالش کرد؟ | نه — با شواهد فعلی نمی‌شود ادعا کرد کار می‌کند |

## ۵. گام بعدی پیشنهادی

تنها آزمون تعیین‌کننده: یک درخواست `connect-udp` با توکن واقعی حساب.
ابزار آماده است و روی ماشین کاربر اجرا می‌شود تا توکن از دستگاه او خارج نشود؛ خروجی فقط کد وضعیت است:
`status 200` یعنی UDP باز است، `403/401` یعنی مجاز نیست، `404/501` یعنی پروتکل پیاده نشده.

## ۶. نتیجهٔ تست با توکن واقعی (اکانت آزمایشی)

ورود انجام شد (شیلد امنیتی + FxA + توکن اکانت + پروکسی‌پس ۵۹۶ کاراکتری) و ماتریس پورت روی سه کشور تکرار شد. سیاست در همه یکسان است:

| مقصد | نتیجه |
|---|---|
| TCP 80 / 443 / 8080 / 8443 | `200` |
| TCP 22 / 53 / 3074 / 4500 | `502 Destination IP Prohibited` |
| TCP 3478 | بدون خطای سیاست (timeout = اجازه داده شد، مقصد جواب نداد) |
| **UDP 80 / 443 / 8080 / 8443** | **`200`** |
| **UDP 3478** (STUN / پارتی PS) | **`200`** |
| UDP 53 / 88 / 500 / 3074 / 3479 / 4500 / 9295 | `502 Destination IP Prohibited` |
| `connect-ip` | `404 not found` |

تکرار روی `muc139` (آلمان) و `lfpb115` (فرانسه): دقیقاً همان جدول.

### معنا
- تونل UDP **کار می‌کند** و پروکسی آن را می‌فهمد و مجوز می‌دهد؛ محدودیت صرفاً «لیست سفید پورت مقصد» است.
- Xbox با پورت‌های ۳۰۷۴/۸۸/۵۰۰/۴۵۰۰ کاملاً مسدود است.
- PS: پارتی/صدای ۳۴۷۸ باز است؛ ۳۴۷۹ و پورت‌های افسانه‌ای ۴۹۱۵۲+ بسته است.
- برای عبور کامل: یک رله (WireGuard/QUIC) روی **UDP 443 یا 3478** لازم است؛ آن‌گاه کل UDP از آن hop می‌گذرد.
